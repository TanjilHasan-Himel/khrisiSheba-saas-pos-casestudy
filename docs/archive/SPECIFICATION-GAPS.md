# SPECIFICATION GAPS AND DECISION REGISTER — Krishi Sheba SaaS

**Status:** Phase 0 correction pass (revision 2) — **awaiting approval; implementation is not authorized.**
**Date:** 2026-11-05
**Revision:** 2 — adds `G-81`–`G-95` and revises `G-03`, `G-07`, `G-60`, `G-69` after the owner's technical review.
**Companion documents:** `ARCHITECTURE-REVIEW.md`, `IMPLEMENTATION-BACKLOG.md`, `PHASE-1-EXECUTION-PLAN.md`, `DECISION-APPROVAL-MATRIX.md`.
**Source documents:** `01-PRD.md` … `08-DECISIONS-AND-OPEN-QUESTIONS.md` (unmodified).

This register lists every requirement that is missing, ambiguous, or internally inconsistent, with a **proposed default**. A proposal is not a decision: it becomes binding only when approved and recorded in the Decision Log (§12) and `DECISION-APPROVAL-MATRIX.md`. Where a choice affects money, stock, or tenant isolation, it is marked **BLOCKING**.

> **Correction-pass warning:** several revision-1 proposals were technically incomplete. In particular, RLS does not authenticate the caller, `store_memberships.role_id` created a second role source, and the default Supabase grants expose new tables to `anon`/`authenticated` until revoked. See `ARCHITECTURE-REVIEW.md` §0 before treating any proposal below as safe.

Severity legend: **BLOCKING** = must be decided before the related migration/endpoint; **High** = needed before that module ships; **Medium** = needed before pilot; **Low** = can be deferred with a documented assumption.
