# ADR 0003 — Identity and session model

- **Status:** Proposed — pending approval (corrected in revision 2)
- **Date:** 2026-11-05
- **Deciders:** Product owner, Lead Architect, Security

> **Correction:** revision 1 named the right components but did not define refresh, CSRF, or the
> `service_role` exception, and implied the httpOnly cookie was automatic. See
> `ARCHITECTURE-REVIEW.md` §0.4.

## Context

The specification leaves the verification channel open and requires a dedicated API. A Supabase
project is already provisioned. Building a second identity system would duplicate security-critical
logic.

## Decision

- **Supabase Auth (GoTrue)** is the identity provider.
- `public.users` stores profile fields only, keyed by `auth_user_id`; it is not the identity source.
  Whether a cross-schema FK to `auth.users` is supported on PostgreSQL 17.11 must be verified in
  F1.2b. If not, use a trigger-maintained unique `auth_user_id`.
- The SaaS app uses a **server-only** `@supabase/ssr` client with PKCE. The session lives in an
  httpOnly, Secure (production), SameSite=Lax cookie with `Path=/`; chunked cookies are handled.
  No token in `localStorage`, `sessionStorage`, a URL, or a client-readable cookie.
- Middleware refreshes with `supabase.auth.getUser()` (validates with the Auth server), not
  `getSession()` alone. A failed refresh clears cookies and redirects to `/login`.
- The API accepts **Bearer only**; it rejects cookie authentication and query-string tokens.
- The API verifies the Supabase JWT (signature via cached JWKS, `iss`, `aud`, `exp`, `nbf`, `sub`,
  algorithm allow-list) on every request. It is never trusted for roles or tenant ids.
- `TOKEN_EXPIRED` triggers exactly one refresh and one retry in Next.js; a second failure logs out.
- Authorization is resolved server-side from `tenant_memberships` and store memberships; store
  membership has no role and only narrows scope.
- CSRF is enforced at the Next.js cookie layer: Origin/Host check on every non-GET route handler and
  Server Action, `SameSite=Lax`, no state-changing GET, no credentialed wildcard CORS.
- `service_role` is used **only** in a narrow server-side admin module for GoTrue operations such as
  revoking refresh tokens on deactivation. Never in the browser bundle, a tenant request path, or
  logs.
- Platform operators require TOTP MFA in P0. Owner MFA is deferred and recorded in the gap register.
- **Google SSO (OAuth)** via Supabase Auth for P0 from the beginning. No password or email-verification friction for onboarding. Store metadata, operational phone numbers, and WhatsApp numbers are collected post-authentication in the application onboarding wizard/settings. Phone OTP deferred pending an SMS provider.

## Rationale

- One identity source, managed password hashing, verification, and MFA.
- The API still owns authorization; the token only proves identity.
- A server-only client is what makes the httpOnly-cookie design real; a browser Supabase client
  would require JS-readable cookies.

## Consequences

- Supabase Auth availability becomes part of the login SLO.
- Email deliverability (custom SMTP) must be configured before onboarding real users.
- Deactivation must revoke refresh tokens and is enforced by the membership check on every request.
  The revocation call needs the `service_role` exception above.
- Cookie size/chunking and host header limits must be verified on the chosen host.

## Alternatives considered

- Custom auth in the API: more code, more risk, no benefit.
- Browser-side Supabase session with direct PostgREST: rejected by ADR 0002.
- Cookie authentication at the API: rejected; the API is Bearer-only to keep CSRF in one layer.
